# 도면 파싱 품질 확인

## 먼저 알아야 할 것

기하는 이제 LLM 이 만들지 않는다. 좌표는 DXF 파서(`ezdxf`)와 벡터화 모델이 만들고,
LLM 은 확정된 기하 위에 방 이름만 붙인다. 그래서 **같은 파일은 언제나 같은 결과가
나와야 한다** — 두 번 돌려 답이 다르면 그 자체가 고장이다.

## 돈이 들지 않는 검증부터

파서와 후처리는 전부 순수 계산이라 API 없이 확인된다. 여기서 먼저 막는다.

```bash
cd services/plan-ingest
.venv/Scripts/python -m pytest tests -q
```

무엇이 도는가.

```
tests/test_golden.py     fixture 세 장의 FloorPlanDoc 을 골든과 비교한다
                         외곽 2% · 방 면적 3% · 방 개수는 정확히 일치
tests/test_dxf_parse.py  단위 — 벽 병합·개구부·실명·설비
tests/test_raster.py     래스터 좌표 변환 (벡터화 모델과 OCR 은 가짜를 끼운다)
```

TypeScript 쪽은 브라우저에서 도는 계산이다.

```bash
npx vitest run tests/plan-polygonize.test.ts tests/plan-polygonize-parity.test.ts tests/plan-edit.test.ts
```

`plan-polygonize-parity` 는 **브라우저의 방 만들기가 파이썬(shapely)과 같은 답을
내는지** 본다. 검수 화면에서 벽을 끌면 브라우저가 방을 다시 만드는데, 그 계산이
파서와 다르면 아무것도 안 고쳤는데 면적이 바뀐다.

## 골든이 빨개졌을 때

**습관적으로 다시 만들지 않는다.** 골든을 시험에 맞춰 고치기 시작하면 그때부터 이
시험은 아무것도 지키지 않는다. 순서는 이렇다.

1. 무엇이 얼마나 달라졌는지 실패 메시지에서 읽는다.
2. 그 변화가 **좋아진 것인지** 판단한다. 방이 하나 사라졌다면 거의 언제나 고장이다.
3. 좋아진 것이 확실할 때만 다시 만든다.

```bash
.venv/Scripts/python tests/make_golden.py
```

## 실제 호출이 꼭 필요할 때

벡터화 모델(RasterScan)이나 라벨러 프롬프트를 바꿨으면 실제로 넣어 봐야 안다.

- **사용자에게 먼저 알린다.** 유료 호출이다.
- 한 번만 돌린다. 여러 번 돌려 평균을 내지 않는다.
- 결과를 그대로 보여 주고 판단을 맡긴다.

## 무엇을 보나

```
방 개수        하나라도 빠지면 고장이다
전체 크기      도면의 외곽 치수와 견준다
실별 면적      폴리곤 면적이다 — 도면에 적힌 면적 글자와는 다를 수 있다
지적 건수      review.flags. 늘었으면 왜 늘었는지 본다
```

## 이 프로젝트가 정한 규칙

1. **좌표는 파서만 만든다.** LLM 에게 좌표를 묻지 않는다. 프롬프트로 고치려 들면
   끝이 없고, 같은 입력에 다른 답이 나온다.
2. **도면은 보정하지 않는다.** 현관이 좁게 그려져 있으면 좁은 게 맞다. 보기 좋게
   고치면 그건 더 이상 그 도면이 아니다.
3. **자동 결과는 확정하지 않는다.** 틀린 것은 검수 화면(`/plan/[jobId]/review`)에서
   사람이 고친다. 파서를 더 조이는 것이 언제나 답은 아니다.

이 순서를 바꾸려면 사용자에게 먼저 물어본다. 한 번 정한 규칙이다.
