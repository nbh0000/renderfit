# 내보내기 전 검사

이 순서를 건너뛰지 않는다. 앞에서 걸린 것은 고치고 다시 처음부터 돈다.

## 1. 정적 검사

```bash
npx tsc --noEmit      # 오류 0이어야 한다
npx eslint .          # error 0. warning은 기존 것만 남아 있어야 한다
npx vitest run        # 전부 통과
npm run build         # exit 0
```

`npm run build`는 `prebuild`로 에셋 스크립트를 돌린다. 키가 없어도 기존 카탈로그를
덮지 않게 돼 있으니 그대로 두면 된다.

## 2. 화면으로 확인

**코드만 보고 "됐다"고 하지 않는다.** 이 프로젝트에서 코드 검토로는 못 잡고 화면에서만
드러난 문제가 여러 번 있었다 — 3D 캔버스가 기본 크기에 멈춰 있던 것, 가구가 바닥에서
떠 있던 것, 대시보드 썸네일이 전부 깨져 있던 것.

개발 서버가 정상 모드인지 먼저 본다.

```bash
curl -s localhost:3000/api/health   # supabase: true 여야 한다
```

그다음 고친 기능이 실제로 보이는 화면을 열어 눈으로 본다. 3D를 건드렸으면 3D를 열고,
평면도를 건드렸으면 실을 골라 속성까지 확인한다.

## 3. 유료 API를 쓰지 않는다

검증하려고 도면 분석이나 이미지 생성을 반복해서 부르지 않는다. 호출 하나하나가
사용자 돈이다. 후처리 로직은 `tests/`의 고정 자료로 검증하고, 화면 확인은 이미 만들어
둔 프로젝트를 연다.

## 4. 커밋

- 커밋 메시지는 한국어로, **무엇을 왜 고쳤는지** 적는다. 증상과 원인을 남긴다.
- 본문 끝에 아래 두 줄을 붙인다.

```
Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
Claude-Session: <세션 URL>
```

## 5. 푸시

`main`에 푸시하면 Railway가 자동으로 배포한다. 따로 할 일은 없다.
GitHub Actions(CI)가 같은 검사를 다시 돌리므로 `gh run list`로 통과를 확인한다.

## 로컬 서버는 프로덕션 모드로

`next dev`는 요청마다 다시 컴파일해서 화면 하나 넘기는 데 1초가 넘는다. 같은 화면이
프로덕션 빌드에서는 10~70배 빠르다.

```
/gallery    1.15초 → 0.07초
/dashboard  0.80초 → 0.011초
```

그래서 사람이 직접 만져 볼 서버는 이렇게 띄운다.

```bash
npm run serve     # 빌드하고 3000번에 띄운다
```

핫 리로드가 없으므로 **코드를 고쳤으면 다시 돌려야 화면에 반영된다.** 고치고 나서
빌드를 잊으면 옛 화면을 보고 "안 고쳐졌다"는 말을 듣는다.

내가 코드를 계속 고치는 동안에는 `npm run dev`를 써도 되지만, 넘길 때는 프로덕션으로
되돌려 놓는다. 그리고 `next dev`가 도는 채로 `npm run build`를 돌리지 않는다 —
둘이 같은 `.next/`를 써서 개발 서버가 요청마다 다시 컴파일하게 된다. 검증용 빌드는
`npm run build:check`다.
